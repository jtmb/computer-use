## What the pinned API actually supports

The package ships a synchronous RPC client (`dist/api/sync/api.js`) that spawns the
real `tsc` as `--api --cwd <dir>` and talks to it over pipes. The project's
`Program` exposes exactly seven non-suggestion diagnostic families:

| Family | Method | Scope |
| --- | --- | --- |
| config | `getConfigFileParsingDiagnostics()` | project |
| program | `getProgramDiagnostics()` | project (includes option diagnostics) |
| global | `getGlobalDiagnostics()` | project |
| syntactic | `getSyntacticDiagnostics(file?)` | file or project |
| bind | `getBindDiagnostics(file?)` | file or project |
| declaration | `getDeclarationDiagnostics(file?)` | file or project |
| semantic | `getSemanticDiagnostics(file?)` | file or project |

`getSuggestionDiagnostics()` exists and is deliberately never called. The four
file-scoped families accept a program file name, so the driver queries **every**
name returned by `program.getSourceFileNames()` (default libraries and external
libraries included). That is a genuinely different control flow from the failed
routes: the earlier TypeScript 6 attempt called a whole-program
`getPreEmitDiagnostics`; the later TypeScript 7 attempt ran the `tsc` CLI on the
full project and was killed with no stdout. This driver never collects the whole
diagnostic set in one response, and it streams a durable receipt while it works.

It does **not** follow that this fits the unchanged memory envelope. The npm
package ships no server-side source, so nothing here proves the native server
releases per-file type-check state as each response is consumed. The measured
cost of the full graph on this route is **unknown and untested**. A successful
tiny-fixture run is API/mechanism evidence only.

## Guarded flow

```text
preflight ── identities, complete graph receipt, overlays, native targets
   └─ run ── supervisor (own process)
        └─ worker ── one API instance, seven families, per-file queries
             └─ receipt.ndjson (write-once, fsync per family / 250 files)
```

- **preflight** hashes the compiler, the API module (its expected digest is
  required), the project config (against the required `configSha256`), root
  files, the graph receipt bytes (against the required `graphReceiptSha256`),
  **every entry of the graph receipt**, the overlay files and the pinned
  originals; it requires the declared native target paths to be clean. Graph
  entries must be unique, absolute regular files whose bytes still match the
  receipt. It never starts a compiler.
- **run** refuses before spawn unless preflight is identity-complete and
  `MemAvailable` is at least 2,816 MiB. It spawns the worker detached, records
  the worker's `/proc/<pid>/stat` start identity, samples the whole owned tree
  every 100 ms and keeps a cumulative registry of descendant identities with
  their PPID/start/group relationships while the root is alive. Root exit does
  **not** end monitoring: the deadline and available-memory floor keep running,
  and the same sampler continues over known surviving descendants and their new
  children, so post-exit RSS can still trip the unchanged owned-RSS guard.
  A bounded post-exit grace terminates only descendants whose recorded start
  identity still matches; a reused or unknown identity is never signalled. After
  the worker exits it **re-runs the complete identity check** (graph source,
  graph-receipt bytes, config, compiler, API module, overlays, native targets)
  and refuses `clean` if anything moved. The caller's stdio handles are released
  even when an unverified descendant survives; such a run is incomplete, never
  clean.
- **worker** verifies the compiler and API-module bytes again, loads the
  configured project, checks the observed file count and sorted unique file
  names, then queries config/program/global and every file of
  syntactic/bind/declaration/semantic. Config diagnostics are classified before
  option checks because an unparseable config still yields a project shell with
  no meaningful options.
- **receipts** are write-once (`wx`). A refused or repeated attempt cannot
  overwrite earlier bytes. The diagnostic stream is ordered (family order, then
  sorted program names) and hashed line by line; the supervisor recomputes that
  digest and rejects mismatches.

### Receipt grammar and per-file evidence

The worker receipt is NDJSON: one `header`, one `graph` observation, then for
each of the seven families in canonical order one `family-start`, the family's
records, and one `family` terminal, and finally one `trailer`.

For the four file-scoped families the records are:

```text
file { family, index, name, diagnostics }   one per sorted program name
diagnostic { family, file, diagnostic }     zero or more, bound to that file
family { family, files, namesSha256, queries, queryDigest, diagnostics, elapsedMs }
```

Every queried file therefore has its own record, including files with zero
diagnostics. The family-start carries the graph name digest, and the terminal
carries the number of queries and a digest over every `(name, diagnostics)`
pair, so the receipt proves per-file coverage rather than only a family total.
The whole-program families carry `namesSha256:null`, `queries:0` and an empty
query digest; their diagnostics carry `file:null`. The trailer's
`iteratedFiles` is the **total** number of file queries across the four
file-scoped families (four times the graph file count for a completed run), not
the last family's count.

`parseWorkerReceipt` rejects, with a reason:

- unknown schema, kind, or extra keys on any record;
- empty lines, a missing/duplicate header, a missing/duplicate trailer, or any
  record after the trailer;
- family records before the graph observation, family-start inside an active
  family, out-of-order or repeated families, diagnostics outside a started
  family or attributed to a different family;
- a missing file record, a file index gap, repeated or non-ascending file names,
  a diagnostic that names a different file, or a file whose recorded diagnostic
  count differs from the records that follow it;
- a family terminal whose query count, name digest, query digest, diagnostic
  count, file count or elapsed value does not match the parsed records;
- a family-start whose file count or name digest differs from the graph
  observation (file-scoped families must declare every program file; the other
  families must declare zero and a null digest);
- trailer family counts/times that do not cover exactly the terminated families,
  or diagnostics/error/warning totals that do not match the records;
- a diagnostic digest that does not match the trailer, and trailer graph/name
  values that do not match the graph observation;
- a `completed` trailer that does not cover exactly the seven families in order
  or that did not query every file in every file-scoped family;
- malformed diagnostics: non-integer code/category/positions, non-absolute file
  names, unknown keys, wrong chain shapes, or nesting deeper than eight.

A **failed** trailer may end in the middle of an active family or file; that
family is recorded as unterminated rather than as a completed family. A
`completed` trailer may not.

## Bounded, fail-closed acquisition

Every file read on an expectation, graph, receipt, compiler, config, root-file or
overlay path goes through one acquisition routine:

- the final component must be a regular file; symlinks, FIFOs, directories and
  other non-regular objects are refused. Linux opens add `O_NONBLOCK`, so a path
  replaced by a FIFO between `lstat` and `open` cannot block the guard; the
  subsequent `fstat` rejects it.
- a byte budget is checked from `lstat` before reading and again during streaming
  reads. Each read requests at most **one byte beyond the remaining budget** and
  the buffer is allocated to that same bound, so a file that grows after the
  first stat is refused after at most `maxBytes + 1` bytes, not after a full
  1 MiB read;
- the compiler and API module are hashed in 1 MiB chunks, never loaded whole;
- the graph as a whole is bounded by 512 MiB and the acquisition deadline
  (120 s); each file is bounded at 128 MiB, the compiler at 128 MiB and the API
  module at 16 MiB;
- a file whose device/inode, size, mtime or ctime changes while it is read is
  refused (`acquisition-changed`) rather than hashed from mixed bytes;
- a missing, unreadable, JSON-invalid or timing-out input fails that route and
  preflight reports the error. It never becomes partial identity.

The process-tree sampler is equally fail-closed: it requires exactly one
`VmRSS: <digits> kB` line, a safe positive PID and task/child identities, a
non-zero owned root RSS, at least one thread, a non-empty tree, and a bounded
number of entries and bytes (64 KiB per proc text read) within a per-sample
deadline. A `Z` task is per-thread state, not a process exit: a leader is only
gone when its same-identity task group has no live (non-`Z`/non-`X`) task, and
RSS is read once from a live task because sibling threads share the `mm`.
`Threads: 0`/`Threads: 1` are never used as a substitute for the task list. A
descendant is only treated as gone on a **proven** missing `/proc` entry or a
zombie group with no live task; a malformed, unreadable or permission-denied
identity, an empty task list, or a live task without a valid `VmRSS` is
`unknown` and fails closed. A child whose PPID no longer matches the
process that enumerated it is a reuse/reparent and is never adopted. The
sampler deadline is cooperative: it is checked between synchronous reads, so a
blocked `/proc` read can still overrun it. The supervisor maps sampler failures
to `monitor-unavailable` and the run is `incomplete`. Sampler injection exists
only as a low-level test seam; `guardedRun` has no injected-sampler path.

Cleanup uses a tri-state ownership observation (`alive`, `missing`, `reused`,
`unknown`). A same-identity leader with at least one live sibling task is
`alive`, so a `Z` leader is not mistaken for completed cleanup while its group
can still allocate. The supervisor signals a process group only while the root is
`alive`, and signals individual descendants only while their recorded start
identity is `alive` at that moment. `unknown` is never signalled and makes
cleanup unverified. Cleanup starts as soon as the child closes and never waits
for the post-run rehash. The receipt records `cleanup.signalled`,
`cleanup.reason`, the descendant signal count and the cumulative observed
process registry. Verified reasons (`worker-close`, `owned-descendants-gone`,
`descendants-terminated`, `no-owned-descendants-observed`) are required for a
clean run; `no-sample`, `descendant-identity-unavailable`,
`descendant-cleanup-unverified` and `descendant-close-timeout` make the run
incomplete. `no-owned-descendants-observed` is scoped to what the samples
observed: polling cannot prove that an unsampled daemon never existed, and the
driver does not claim that.
