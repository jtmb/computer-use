# README Layout Reference

Read this general checklist explicitly before a substantial README layout
change. It supplements, but never overrides, the consumer project's own style,
branding, accessibility, or length rules.

## Plan for the reader

1. Identify the README's audience and the first question it should answer.
2. Lead with a clear project identity and a concise purpose statement.
3. Put the most useful next step early, such as a verified quick start or link
   to an authoritative setup guide.
4. Group capabilities, usage, and documentation links into scannable sections.
5. Keep detailed configuration, API references, and maintainer procedures in
   their existing focused documents when available.

## Accuracy and accessibility

- Preserve established names, logos, colors, image paths, and alt text unless a
  branding change is requested.
- Use only verified badges, demos, examples, compatibility, status, and license
  claims. Label samples and limitations clearly.
- Avoid requiring a demo, badge, section order, or particular line count unless
  the consumer project has documented that requirement.
- Prefer readable headings and lists over dense prose or artificial line
  wrapping. Do not remove safety or prerequisite information to shorten a page.
- Resolve local links and inspect a rendered preview when the available tools
  allow it; describe any unverified rendering or external destination honestly.
